# v0.6.0

Range: `v0.5.1..v0.6.0`. Workspace `0.5.1` -> `0.6.0`. Breaking: the `azure`/`gcs` bucket drivers are gone, the default s3db spool directory moves, release asset objects get per-upload names, and a sister handshake needs both sides on this version. See **Ops**.

## Breaking

- `s3db`/`s3db-crypto` `v0.4.6` -> `v0.6.1`. s3db v0.6.0 drops its Azure and GCS backends, so `driver = "azure"` and `driver = "gcs"` under `[buckets.<name>]` no longer parse (`BackendConfig` is `#[serde(tag = "driver")]`, flattened into `BucketConfig`): only `s3`, `r2` and `local` remain. `config`'s `AzureParams`/`GcsParams` re-exports and the setup wizard's `azure`/`gcs` options (`setup.rs`, `backend_config_from_form`) are removed; a prefill from an Azure/GCS config starts blank.
- `config::resolve_local_dir`, applied in `Config::load_from` and the setup wizard: `[buckets.<name>.resilience] local_dir` left at s3db's `./local` default becomes `<data_local_dir>/gitquarry/<bucket name, non-alphanumerics -> _>` instead of resolving against each process's cwd; any other relative path resolves against the directory holding `gitquarry.toml`. s3db v0.6.1 keeps one `<spool_root>/<random>.redb` per open backend and adopts orphaned files there, a pre-0.6.1 `spool.redb` included.
- `backup::dest::resolve`: a `path:` backup destination opens with `LocalEngine::Redb` instead of the retired `Files` engine, and refuses a non-empty directory without `s3db.redb`, naming `s3db-local-migrate <dir>`.
- `storage::remote::AssetMeta.object` (`#[serde(default)]`, omitted when `None`): each release asset upload is stored as `releases/<tag>/assets/<unique_asset_object>` (`<32 hex random>-<filename>`) and the name recorded in the release metadata. `Remote::{upload,download,delete}_asset` take that object name; `AssetMeta::object_name` falls back to `filename` for assets stored before. `domain::release::add_asset` deletes its own object on a definite `Cas::Conflict`, so two concurrent uploads of one filename can no longer leave the loser's bytes under the winner's sha256/signature. A pre-0.6.0 binary reads `releases/<tag>/assets/<filename>` and can't serve assets uploaded by this one.
- Federation sister handshake (`gitquarry-federation`): `sister::request` stages the handshake secret as the instance's own peer credential before dialing, returns it, and refuses an already-confirmed sister. `sister::receive_handshake` dials back `POST <registered web_base_url>/_federation/sister/verify` (`instance_client::verify_sister_secret`, answered by `sister::verify_staged_secret`) and confirms only if the peer vouches for the secret, re-reading the `Peer` and writing it under CAS after the round trip. `POST /_federation/sister/handshake` answers 503 without `own_web_base_url`/`own_git_base_url`. Secrets compare in constant time (`subtle`), `sister_by_secret` included. A peer without `/_federation/sister/verify` can't complete a handshake with this side.

## Added

- Passkeys. `gitquarry_auth_crypto::webauthn`: a rustls-only WebAuthn relying party (no `webauthn-rs`, which needs openssl) over `ciborium`/`p256`/`ed25519-dalek`; `ES256` (-7) and `EDDSA` (-8); checks ceremony type, challenge (constant time), origin and `crossOrigin`, rpIdHash, UP/UV, credential id length (`MAX_CREDENTIAL_ID_LEN` 1023), signature and sign counter (`CounterRegressed`). Attestation is parsed and ignored (equivalent to `"none"`).
- `auth::entities::Passkey` in `.conf/passkeys`, keyed by `access::passkey_key` (SHA-256 hex of the credential id), owner index `.conf/index/passkey-owner/<owner_uid>`. `access::MAX_PASSKEYS_PER_USER` 16, `MAX_PASSKEY_LABEL_LEN` 64. `domain::passkey::{register,list,remove,verify}`: register is create-only, verify matches the user handle to the owner uid and writes the counter back under CAS (`ConcurrentUse`). `domain::user::delete` removes the account's passkeys; `backup::inventory::classify_conf` carries `.conf/passkeys/` as entities.
- `ServerSettings::public_url` (`.conf/global.json`), set from `POST /_settings/network` and checked by `RelyingParty::from_public_url` (`https`, or `http` on `localhost`/`127.0.0.1`; no IP hosts, no credentials). Unset means passkeys off and every passkey route answers 404; the relying party never comes from `Host`.
- `auth::web::passkey` routes: `POST /_account/passkeys/{begin,finish,remove}`, `POST /_login/passkey/{begin,finish}`, `POST /_login_totp/passkey/{begin,finish}`, `GET /_assets/passkey.js`. Registration and removal need `reauth::require_reauth_for_credential_change`; the challenge lives in the sealed single-use `passkey-challenge` cookie (`CHALLENGE_TTL_SECS` 300, bound to purpose and username, spent-set LRU 4096). Creation options: `residentKey`/`userVerification` `required`, `attestation: "none"`, `excludeCredentials` the account's own.
- `/_login`: a discoverable passkey signs in alone (empty `allowCredentials`, UV required) and counts as both factors; needs `login_enforced`. `/_login_totp`: a passkey of the pending account replaces the code (UV preferred), refusals counted in the same `ctx.login_attempts` bucket. `login::issue_session` is shared by all three paths. Audit actions `passkey.register`, `passkey.remove`, `passkey.login`, `passkey.second_factor`.
- `POST /_account/passkeys/begin` takes an optional `kind` (`AuthenticatorKind`): `security-key` -> `hints: ["security-key"]` + `authenticatorAttachment: "cross-platform"`; `device` -> `hints: ["client-device", "hybrid"]`, no attachment. The security page has one button per kind.
- `gitquarry-federation` is back in the workspace: lib plus `gitquarry-federation` binary, configured by `gitquarry-federation.toml` (`GITQUARRY_FEDERATION_CONFIG`), on the same bucket and passphrase. Core gains an optional `[federation]` in `gitquarry.toml` (`internal_bind`, `internal_token`, `federation_url`; absent = off), `internal_api::run_server` on `internal_bind` (`/_internal/*`), and webui routes `/_remote/{peer}/{*repo}`, `/_peers`, `/_account/tokens`, `/_remote_pulls/comment`, `/_api/*`, `/_federation/gossip/{announce,peers}` that answer 503 without it. `git::http::authenticate` resolves federation tokens after `gqpat_` PATs. Additive, `#[serde(default)]` fields: `User.is_federation_moderator`, `RepoConfig.forked_from_peer`.
- `gitquarry repack --max-pack-size BYTES`, default `git::DEFAULT_MAX_PACK_SIZE_BYTES` (1 GiB), passed to `git repack --max-pack-size`.
- `gitquarry serve --mirrors-large-repo-threshold` (default `DEFAULT_MIRRORS_LARGE_REPO_THRESHOLD` `"1G"`), falling back to `ServerSettings::mirrors_large_repo_threshold`: `mirror::gc::sweep_once_impl` skips age eviction for a mirror at or above it; the size pass still applies.
- `ExternalMirror.branch_patterns` (empty = every branch), set in repo settings as a comma list: `engine::sync_mirror_once` syncs only matching `refs/heads/*` (`git::codeowners::segments_match`, `*` within a segment, `**` across). Tags are never filtered.
- `serve::run`: `s3db::txn::recover_stale` every `STALE_TRANSACTION_SWEEP_INTERVAL` (600 s), not only at startup; `recover_spool` (`SpooledBackend::recover_pending`) at startup and every `SPOOL_RECOVERY_INTERVAL` (60 s), replaying what hooks and CLI commands left spooled. `storage::build_backend` returns `s3db::ResilientBackend { backend, spool }`.
- `POST /_account/security` with `security_action=revoke_sessions`: `domain::user::revoke_sessions` bumps `User::session_epoch`, audit action `user.revoke_sessions`, then redirects to `/_login`. Rendered as a "sessions" section on the security page.
- `migrations::repo_permission_index` (data version 2, `.conf/data-version.json`), run by `migrations::run_pending` at startup or `gitquarry migrate`: indexes every existing `User::repos` grant under `.conf/index/repo-permission/<repo_uid>`. Additive and idempotent.

## Changed

- Setup wizard served at `SETUP_PATH` (`/_setup`, `GET`/`POST`); `GET /` redirects there with 303. It also serves `/_assets/*` through the new `webui::asset_routes`.
- Last-push is stamped by a push, merge or mirror pull to any branch (`mirror::hook::run_pre_receive_hook`, `domain::merge_request::merge`, `engine::persist_pulled_ref_to_s3`), not only the default one. Tags and branch deletions don't count.
- `argon2` 0.5.3 -> 0.6.0 (`password::hash` drops `SaltString`; 0.5-era PHC hashes still verify), `russh` 0.63.3, `tower-http` 0.7.1, `dirs` 7.0.0, `reqwest` 0.13.5.
- Shared dependencies declared once in `[workspace.dependencies]`; every member inherits `[workspace.package]`, `gitquarry-federation` included.
- `git::http`: `upload_pack_response` streams the request body into `git upload-pack` and its stdout back out (`stdout_chunks`, 64 KiB reads, fused) instead of buffering both; a `receive-pack` body is spooled by `spool_body` to an unlinked tempfile under `mirrors_root`, capped at `MAX_PACK_BODY_BYTES` (16 GiB, 413 past it), before `open_mirror` takes the exclusive repo lock.
- `serve::run`: an `Err` reading `.conf/global.json` fails startup (`reading the bucket config (.conf/global.json)`) instead of warning and running on `ServerSettings::default()`. An absent object still reads as the defaults.
- `gitquarry-federation` logs through `tracing` (`tracing_subscriber`, stderr, `RUST_LOG`, default `info`) instead of `eprintln!`.
- `[profile.release]`: `debug = false`, `incremental = false`. New `.dockerignore`: `target/`, `.git/`, `crates/*/target/`, `*.tar.gz`, `node_modules/`, `.env`, `gitquarry.toml`.

## Fixed

- `webui::repo::releases`: `validate::validate_rev` on the trimmed tag in `handler_edit_post`, `handler_delete_post`, `handler_upload_asset_post`, `handler_delete_asset_post` and `handler_generate_notes_post`.
- `storage::merge_requests::list_merge_requests` skips nested `<n>/comments/…`/`<n>/reviews/…` names, which listed as a phantom MR #0.
- `auth::domain::user::set_repo_perm` goes through `domain::repo::set_permission`, so a grant made from the admin user page lands in the repo permission index and shows (and can be revoked) on the repo's grid. `domain::user::create` indexes initial grants too.
- `settings::web::require_admin_or_federation_moderator` (`/_peers`) required nothing while `login_enforced` was false; it now requires the bootstrap grant.
- `webui::repo::handler_repo`: a logged-out visitor of `?view=settings*` returns to `/{repo}?view={view}` after login; `repo_settings::require_repo_authority` sends `return_to=/{repo}` with its leading slash, which `is_local_redirect` refused.
- `setup::render_form` no longer writes the stored `secret_access_key` or `passphrase` into `value=`. A blank one keeps the stored value only when `same_destination` holds: same driver and bucket, plus region/endpoint/access key id/path style/`allow_insecure_http` for `s3`, account id/access key id for `r2`.
- `serve::run` drops the startup backend before the prefilled setup wizard reopens it (a local redb admits one handle per process).
- Data migrations with an empty summary log `nothing to change`.
- Federation: `sister::receive_handshake` never overwrites a confirmed sister's secret; `gossip::handler_announce` caps candidates at `MAX_ANNOUNCE_CANDIDATES` (64) and runs `validate::validate_instance_url` before dialing any.
- `git::http::middleware`: a path that only ends like a git-HTTP endpoint falls through to the web UI unless its prefix resolves to a real repo (`ctx.resolve_repo`), so e.g. a file named `info/refs` under `/owner/repo/blob/main/` no longer answers 404.
- `git::http::ClientError` (`BadRequest`/`TooLarge`): a missing or unsupported `?service=`, an invalid LFS oid, a truncated body or bad gzip answer 400, a body over its cap (`read_capped`, `http_body_util::LengthLimitError`) 413, LFS kinds in `lfs::error_response`'s JSON shape; none of them logs an `error!` any more.
- `git::http::PackBody` undoes `Content-Encoding: gzip`/`x-gzip` on upload-pack and receive-pack bodies (anything but `identity` -> 400). git's HTTP client gzips any upload-pack request over 1 KiB, which `git upload-pack` can't read raw.
- `GET info/refs?service=git-receive-pack` counts as part of the push: exempt from `git_rate_limiter` and `mirror::sync_external_before_serving`, like the `POST` after it.
- Push events: `events::mirror_refs` reads the refs off the locked mirror before and after `receive-pack` (HTTP and SSH) instead of the bucket manifest, which the caching backends still served pre-push, so the diff came out empty and no `RepoEvent::Push` fired.
- `mirror::hook::run_pre_receive_hook` sets `manifest.head` on an empty repo only from a `refs/heads/*` ref; a tag pushed first pinned HEAD for good.
- `mirror::gc::prewarm_recent_mirrors` skips nested peer mirrors (`_remote/<peer>/<repo>`): syncing one from a bucket with no manifest for it deleted every ref.
- LFS locks: `storage::lfs_locks::create_lock` writes the record, then a create-only path claim at `repos/<uid>/lfs-lock-paths/<base64url path>`, so two concurrent locks on one path give one 201 and one 409; a claim whose record is gone is taken over by CAS. `delete_lock` releases the claim before the record. `backup::inventory::classify_repo` and `domain::repo::NOT_INHERITED_BY_A_COPY` cover `lfs-lock-paths/`. `list_locks` and unlock propagate read/delete errors instead of dropping a lock (a skipped one read as a free path). `git::lfs::query_param` percent-decodes `?path=`/`?id=` (`form_urlencoded`).
- `storage::settings::bump_lfs_bytes` retries a CAS conflict (5 attempts, `cas_retry_backoff`) and logs what's left, instead of dropping the bump whenever a push hook had just rewritten the repo config.
- `domain::repo::{delete,restore}` go through `set_deleted_at`: a fresh read per attempt, 5 attempts, and the visible/deleted indexes change only after the `deleted_at` write lands.
- `/_releases/asset_upload/{*repo}` gets `DefaultBodyLimit::max(MAX_ASSET_UPLOAD_BODY_BYTES)` (2 GiB + 1 MiB); axum's 2 MiB default refused any larger asset. `read_text_field` caps `tag`/`csrf`/`signature` at `MAX_TEXT_FIELD_BYTES` (64 KiB).
- `gitquarry_gpg::ScratchHome` creates and removes the scratch homedir on the blocking pool.
- External mirrors: `engine::sync_mirror_once` also walks `last_synced` keys, and `access::forget_ref` drops a ref gone from both sides; its stale sha made a recreated ref look like one side of a deletion, never synced.
- MR sync (`mr_sync`): export only `MrStatus::Open` MRs whose `source_repo` is this repo; `ExternalMirror.mr_export_failures` (local MR -> attempts) stops an export after `MAX_MR_EXPORT_ATTEMPTS` (5). Import: the forge clients cut at `stamp::later` (moved to `gitquarry_forge_clients::stamp`) instead of a string `>`, keeping MRs updated at the cursor instant; `ExternalMirror.mr_discovery_cursor` is held at the oldest failed import so the next tick retries it.
- `merges::handlers::handler_merge_post`: a conflict on an async submit (`ASYNC_HEADER`) answers 400 with the paths instead of a redirect whose full page landed inside `#mr-actions`.
- `merges::handlers::handler_bulk_post` parses its body with `form_urlencoded`, so repeated `numbers` fields work; every submission with a selection was a 422.
- Appearance and PAT forms post `appearance_action`/`pat_action` instead of `action`, which shadowed the `data-async` form's `.action` (`app.js` posted to `[object HTMLInputElement]`).
- `remote_repo::render_remote_fork_form` posts to `/_fork/{repo}` (bare `/_fork` has no route); `fork::dest_name` validates and slugifies a peer fork's name like a local one.
- `components::label_pill` (also used by repo settings' label preview) emits `data-label-color`, painted by `style/app.js` through the CSSOM; the `style=` attribute was dropped by `style-src 'self'`.
- i18n: `<html lang>` from `Locale::code`; the peer fork form, `diff_view` toggle, `shared::saved`/`saved_to_bucket` flashes (profile, groups), `repo_settings::permission_saved` and `repo_name_needs_alnum` are localized.
- Federation: core's webui proxies `POST /_federation/sister/{handshake,verify,ban-event}` and `GET /_federation/sister/bans` (`federation_proxy::proxy_public`), so sisters reach each other on the public port. `sister::apply_ban_event` ignores a ban for a peer already banned on another source's word, keeping a local ban local so its unban still propagates; `GET /_federation/sister/bans` leaves out bans learned from the caller. `domain::token::revoke` returns `Result<bool>`, and `/_account/tokens` says `no such token.` or `revoke failed: …` instead of always `revoked.`. `web::api_pulls::authorize`: a token-lookup failure answers 500 and a core lookup/authorize failure 502 (`upstream_error`) instead of 401/403/404. `rate_limit::Bucket` sweeps idle keys once per window.

## Security

- `/_setup`: `setup::run` takes a per-process 192-bit hex token (`gitquarry_auth_crypto::random_token`, never stored) and logs `http://<web-bind>/_setup?token=…` at startup. `GET` and `POST` compare it in constant time (`subtle`) and answer 403 with one page for a missing or a wrong token; it rides in the form as a hidden `token` field, so it doubles as CSRF defence. Before, whoever reached the port first picked the storage and created the admin.
- `domain::user::remove_pubkey` bumps `session_epoch`; `domain::passkey::remove` calls `domain::user::revoke_sessions` before deleting the record. `revoke_sessions` retries a lost CAS (5 attempts) instead of returning `Cas::Conflict`, which left the session it meant to end alive.
- `webui::secure_cookies_middleware` (inside `request_cache_middleware`): when `ServerSettings::public_url` starts with `https://`, `cookies::force_secure` adds `Secure` to every `Set-Cookie` whatever `X-Forwarded-Proto` says; a value that isn't visible ASCII is kept as is. A settings read error falls back to the per-request answer with a warning.
- `csrf::anchor_cookie`: with no session, `csrf_field`/`require_csrf` derive the token from `bootstrap::BOOTSTRAP_COOKIE`, so admin forms in the bootstrap window carry one (they rendered none and failed verification).
- `git::http::client_key` with `trust_forwarded_for`: the last `X-Forwarded-For` hop, the one the proxy appended, instead of the first, which the client chooses.
- `repo_settings::touches_privileged_member`: a `set_perm` on someone who already holds `Maintainer`+ needs `can_manage_repo_members_for` (owner tier); a Maintainer could demote or strip an Owner.
- `escaping::is_local_redirect` rejects any control or whitespace character: the URL parser strips tab/CR/LF, so `/\t/evil.com` reached the browser as `//evil.com`.
- `language_tag::language_tag` returns `plaintext` unless the extension is `[a-z0-9_+-]`; it is spliced unescaped into `class`, and a pushed file `x."onmouseover=…` broke out. `repo::diff::header_path` strips git's C-quoting.
- `gitquarry_gpg::fingerprint` refuses a blob with more than one `pub:` primary key; the whole blob is imported at verify time, so a second key verified under the one recorded fingerprint.
- `mr_sync::imported_author`: imported MR and comment authors are stored as `<host>/<login>`, which can't equal a local username (no `/`); a same-named local user got author rights over the imported MR.
- Federation: `web::session::forwarded_user_uid` refuses an empty uid, the key the instance's own sister secrets live under. `GossipTable` resets `first_seen` and `reported_by` when a candidate's URLs change. `api_pulls::handler_create_post` requires read access on a different `source_repo`. `federation_proxy::capped_body` caps `proxy_public`/`proxy_peers`/`proxy_tokens` bodies at `MAX_PROXIED_BODY_BYTES` (2 MiB, 413) instead of `usize::MAX`. `gitquarry_wire::ipc::token_matches` compares `x-internal-token` in constant time. `sister::apply_ban_event` validates `peer_name`/`git_base_url`, files an unknown banned peer as `BrowseOnly`, and lets a sister lift only a ban it put here (unban drops `access_level` to `BrowseOnly`); `reconcile_with_sister` skips a bad entry instead of aborting. `validate::validate_web_base_url` (`http(s)://`) and `validate_git_base_url` (`http(s)://`, `ssh://`) replace `validate_instance_url`: `git://` is refused for peers, gossip candidates and ban events.
- `rustls` 0.23.45 -> 0.23.46 (RUSTSEC-2026-0346..0349). `.cargo/audit.toml` ignores RUSTSEC-2023-0071 (Marvin): both `rsa` users only verify (russh/ssh-key client keys, openidconnect JWTs).

## Ops

1. A bucket on `driver = "azure"` or `"gcs"` has no path forward in this binary: move it to `s3`, `r2` or `local` with v0.5.1 first. No migration tool ships for it.
2. With `resilience.local_dir` unset or `./local`, the spool moves to `<data_local_dir>/gitquarry/<bucket>` (`~/.local/share/gitquarry/<bucket>` on Linux). Writes still pending in the old `<cwd>/local` are not replayed from the new place: to keep them, set `local_dir` to that directory (now resolved relative to `gitquarry.toml`), where s3db v0.6.1 adopts the old `spool.redb`.
3. A `path:` backup destination written by the `files` engine: `s3db-local-migrate <dir>` before the next backup.
4. Data migration 2 (`repo-permission-index`) runs on its own at first startup.
5. Passkeys stay off until `public_url` is set in `/_settings/network`.
6. The setup wizard (first run, or a config with no admin yet) opens only through the `/_setup?token=…` link printed in the server log; the token changes on every start.
7. Federation sisters: both instances on this version, each with `own_web_base_url`/`own_git_base_url` set in `gitquarry-federation.toml`, or the handshake fails (503 on the receiving side). Confirmed sisters are untouched.
8. `trust_forwarded_for = true` needs a proxy that appends (or sets) `X-Forwarded-For`; behind chained proxies the last hop is the innermost proxy's peer.
9. Startup now stops if `.conf/global.json` can't be read or decrypted: fix the bucket endpoint, credentials or passphrase rather than expecting defaults.
10. Release assets uploaded by this version aren't readable by an older binary: don't roll back past it once assets have been added.
11. Docker images: `gitquarry.toml` is no longer in the build context; mount it at runtime.
