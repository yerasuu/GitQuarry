# v0.4.2

Range: `v0.4.1..v0.4.2`. Every crate in the workspace moves `0.4.1` ->
`0.4.2`; they share one version so a deploy can be named by a single number.

Patch: one fix on the merge-request page and one affordance on the release
form. Nothing to do at deploy time.

## Fixed

- **A merged merge request said it had changed nothing.** The page compared
  the target branch against the source branch, and once the merge lands the
  source is an ancestor of the target — so the three-dot diff between them
  is empty, and every merged request rendered with no diff, no stat and no
  commits. It now falls back to the merge commit against its own first
  parent, which is what the request actually landed, exactly as it already
  did for a request whose branch was deleted after merging.

  A rebase-merged request keeps comparing branch to branch: its replayed
  commits carry different shas, so they aren't contained in the target and
  that comparison is still the truest answer available.

## Added

- **The release form suggests the repo's tags.** A release can only ever
  name a tag that already exists, so the one required field on that form
  used to be a memory test. It now offers the repo's tags the same way the
  new-merge-request form offers branches — and leaves out the tags that
  already have a release, since those would only earn a rejection.
