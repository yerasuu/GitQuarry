# v0.4.1

Range: `v0.4.0..v0.4.1`. Every crate in the workspace moves `0.4.0` ->
`0.4.1`; they share one version so a deploy can be named by a single number.

Nothing in this server changed. The storage engine pin moves from `s3db`
v0.4.2 to v0.4.3, whose library half is byte-identical — the release exists
so a deployment names the tag whose tooling matches the bucket it operates.

## Changed

- **Pinned to `s3db` v0.4.3.** What that tag adds is all in the
  `s3db-inspect` operator tool, not in anything this server links:
  - `rebind`, which re-seals an object whose ciphertext was copied to a new
    key without being decrypted and re-sealed first. Every object is sealed
    with its own storage key as associated data, so a server-side copy or a
    prefix rename leaves bytes that authenticate against a key they no
    longer live at — the object then reads as corrupt, with the same error a
    wrong passphrase gives.
  - `get` now says when an object is stream-sealed (a release asset, a pack)
    instead of reporting it as a decrypt failure. Those are written chunk by
    chunk in a different on-disk format, and calling that corruption sends
    whoever is mid-incident after the wrong thing.
  - The three s3db crates inherit their version, edition, MSRV and licence
    from the workspace rather than each carrying its own copy.
